# User Story：企业平台工程师集成 Dune

> 关联规范：[Dune 底层协议与 SDK](../spec.md) · [Gateway 与 daemon 协议](../runner-tunnel-protocol.md) · [上层产品模型](upper-layer-products.md)

## 用户目标

作为企业平台工程师，我希望在已有云基础设施和开发机上部署统一执行入口，使用 Dune 协议与 SDK 构建企业研发工具，而不必自行实现远程进程、PTY、Agent 连接和能力传输协议。

企业不必预先拥有 Agent 平台。首个闭环可以是远程控制一台开发机中的 Agent，支持长期开发，再由上层扩展托管环境或即时任务。

## 职责分界

Dune 提供：

- 标准能力与扩展能力接口、协议及 SDK。
- 执行认证、授权和路由的 Gateway。
- 运行于 sandbox 或开发环境内的控制 daemon。
- 由能力插件或 adapter 提供的文件、进程、终端和 Agent 等执行能力。
- 必需的有界内存连接与执行状态。

企业上层负责：

- 用户、Tenant、项目、Runner 和 Fabric 关联。
- 云资源申请、开发机登记及环境生命周期。
- Profile 保存、选择、版本和完整传递。
- 业务用户权限及业务用户到 OS 账号的映射。
- 工作台 UI、外部入口、任务编排与业务状态。
- 可选 Provider 能力的接入和产品化表达。

## 最小接入流程

```text
准备一台现有开发机
  -> 安装 daemon 与所需能力插件、Agent adapter
  -> 配置可信 Gateway 及经过认证的路由
  -> 上层完成业务用户鉴权与 OS 账号映射
  -> 生成授权范围明确的可信执行上下文
  -> 使用 SDK 发现目标能力
  -> 完整提交初始化 Profile
  -> daemon 校验后执行环境和 Agent 初始化
  -> 通过 ACP 或 PTY 启动并远程操作 Agent
  -> 上层提供项目入口和持续连接体验
```

Gateway 与相关服务可以合并部署并使用统一访问路径，但部署合并不取消认证、授权和可信调用边界。

## root daemon

root daemon 可以在同一主机上按授权 OS 身份执行操作。业务用户到 OS 账号的映射由上层完成，daemon 不管理企业用户目录。

可信上下文规定授权上限。Profile 可以声明执行身份，包括 root；请求必须落在上限内，身份冲突或信息不足时拒绝执行。

创建 OS 账户属于可能产生系统副作用的初始化操作。环境 Profile 或 Agent Profile 都可以包含此类初始化，但必须获得相应权限。

## 非 root daemon

非 root daemon 的所有请求使用同一个 OS 用户，不提供业务用户级 OS 身份隔离，也不承担业务用户级授权。

它只接受可信 Gateway 的调用。Gateway 必须先完成入口认证授权，上层也必须完成业务用户权限检查。不能把“使用同一个 OS 用户”解释为允许匿名请求。

## 可复用配置与插件

用户可以直接选择 Fabric 和环境初始化配置。企业可以通过二次开发提供 preset，组合已有配置；preset 不是 Dune 必须管理的新业务资源。

Profile 由上层持久化管理，以 kind=environment 或 kind=agent 的完整 payload 通过 SDK 传递，由 daemon 解析执行；上层不预先将其展开为命令。

插件和 adapter 声明实际能力。标准能力由上层统一界面呈现；扩展能力可以通过类似 MCP UI 的插件视图呈现。UI 的加载、授权和与 SDK 的受控交互由上层产品负责，Dune 本身不提供 UI。

## 数据与运行状态

Runner、Tenant、Profile 和任务状态由企业上层保存。工作内容与 Agent 会话数据留在执行环境。

Dune 不保存业务数据，但可以维护内存中的连接、路由、进程控制和短时缓冲。企业不得把这些短时状态当作永久会话历史或任务数据库。

## 验收条件

- 企业仅凭传统云基础设施或开发机即可完成首个远控闭环。
- 未建立上层 Runner 管理服务时，底层协议与 SDK 仍可独立使用。
- 上层身份映射和 daemon OS 执行边界清晰且可验证。
- Profile 请求 root 或创建账户时无法突破授权上限。
- Gateway 和 daemon 的部署方式不改变入口鉴权要求。
- 企业能够在不修改底层资源模型的前提下增加 UI、Runner 管理和外部入口。
